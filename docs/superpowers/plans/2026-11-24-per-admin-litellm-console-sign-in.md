# Per-admin sign-in to the LiteLLM console (option B)

**Status:** design for review, 24 Nov 2026. No code yet.
**Relates to:** `docs/components/litellm.md` "Access", `docs/superpowers/plans/2026-10-29-litellm-integration.md` Task 1.2.

## Summary

Today every OS admin who opens Admin → LLM Gateway is signed in to LiteLLM as **one shared UI
account** (`UI_USERNAME` / `UI_PASSWORD`). So LiteLLM's own records cannot tell admins apart, and
that account is also a password login anyone could try. Option B gives **each OS admin their own
LiteLLM `proxy_admin` user**. The OS creates it when someone becomes admin and removes it when they
stop being admin or are deactivated. The OS sets a random password and keeps it, and completes
LiteLLM's forced first-login password change server-side, so the admin never sees or types a
LiteLLM password. The OS caches one LiteLLM session **per OS user**, not one global session. Once
every admin has their own user, the shared env login is switched off (`disable_env_credential_login`).
LiteLLM's `/audit` is Enterprise-only, so the **OS audit log is the system of record** for who
opened the console. Every LiteLLM UI login mints a 24-hour key ($1 budget, team
`litellm-dashboard`), so sessions are cached and reused, not re-minted on every page.

Facts about LiteLLM 1.109.1 (owner's notes from dev, 23 Nov):

- A user created by the API has to change their password at first UI login.
- `/audit` is Enterprise-only.
- Every UI login creates a 24-hour key with a $1 budget in team `litellm-dashboard`.
- `disable_env_credential_login` switches off the `UI_USERNAME`/`UI_PASSWORD` login.

Problems with today's setup:

1. LiteLLM cannot attribute console actions to a person.
2. The shared password is a standing credential.
3. A browser keeps the LiteLLM cookie after OS logout. A second admin on the same browser would
   reuse it. A demoted admin is stopped by the OS path gate, but the cookie stays valid at
   LiteLLM until it expires.
4. Every cache miss creates another 24-hour dashboard key.

## 2. Target design

### 2.1 One LiteLLM user per OS admin

| | |
|---|---|
| LiteLLM `user_id` | `os-admin-<uid>` (distinct from the `os-u-<uid>` MCP users in the Phase 5 design, which never get a UI role) |
| `user_role` | `proxy_admin` |
| `user_email` | the admin's OS email, for display in LiteLLM only |
| Password | 32 random bytes (base64url), generated by the OS, **never shown** |
| Models / budget | none on the user itself. UI dashboard keys carry LiteLLM's own $1 cap |

### 2.2 Password storage

The password is stored encrypted in Postgres: table `litellm_admin_credentials (uid, litellm_user_id,
sealed_password, key_id, rotated_at)`. It uses the same AES-256-GCM pattern and the same database as
`agent_system_keys` (`docs/components/litellm.md:505-530`), with AAD = uid. It is never in a trace,
a log or an API answer. Rotation means setting a new random password through the admin API and
dropping that user's cached session.

### 2.3 Provisioning and deprovisioning (a reconciler, not inline calls)

`startLiteLlmAdminReconciler`, same shape as `startTrinoRulesReconciler`:

- **Triggers:** boot, `onDirectoryChange` (debounced and serialised), and a periodic pass every
  10 min (jittered) to catch manual edits in LiteLLM.
- **Desired set:** active OS users with role `admin`.
- **Actual set:** LiteLLM users whose id starts with `os-admin-`.
- **Plan, then apply:**
  - **create** missing (`/user/new`, then the first-login flow 2.4);
  - **demote or delete** extra (the user is deleted; their dashboard keys are blocked or deleted
    by `user_id`);
  - **block** a deactivated admin before deletion, so a cached session dies at once.
- **Order on demotion or deactivation:** drop the OS session cache entry → block the LiteLLM user's
  keys → delete the user → audit. Each step is idempotent and retried.
- **Outcome:** typed and visible in Platform → Components & Health (as `lastReconcileOutcome` does
  for Trino rules). It never fails silently.
- **Never touches** LiteLLM users it did not create (no `os-admin-` prefix), except when the
  shared env login is retired (2.6).

### 2.4 The forced password change, server-side

LiteLLM requires a password change at first login for an API-created user. The OS does this once,
in the reconciler, right after creation:

1. Log in with the initial random password.
2. Call LiteLLM's password-change step with a **second** random password.
3. Store only the second password.
4. Log in again to prove it, then cache that session.

The exact endpoint is taken from the LiteLLM 1.109.1 source and pinned with a contract test, so
an upgrade that changes it fails CI, not production. If the step fails, the user stays
"provisioning", the console shows "Your LiteLLM account is being set up", and the next pass
retries.

### 2.5 Per-OS-user session cache

`tool-sso-litellm.ts` changes from one global cache to `Map<osUid, {cookies, at, keyExpiresAt}>`:

- `getLiteLlmSessionCookies(user)` takes the OS user.
- The TTL stays below the 24-hour dashboard key and LiteLLM's JWT lifetime: 8 hours or until the
  key's expiry minus 10 min, whichever is sooner. This means **one login, and one dashboard key,
  per admin per 8 hours**, not one per cache miss.
- Bounded size (number of admins). Entries are evicted on demotion or deactivation by the
  reconciler.
- Single flight per uid, so a page that fires ten sub-requests logs in once.
- The route passes `user` (`route.ts:59`).

**Cookie binding:** the browser cookie must not outlive or cross OS users. Choose one of:

- **(a) Recommended:** never persist the LiteLLM cookie on the browser. Strip any inbound LiteLLM
  session cookie at the proxy and inject the cached per-uid cookie server-side on every request.
  This changes `tool-proxy.ts:497` for LiteLLM.
- **(b)** Keep persisting it, but also set an OS-signed cookie naming the uid, and refuse (then
  re-mint) when it does not match the OS session user.

(a) is simpler and closes problem 3. The cost is one map lookup per proxied request.

### 2.6 Retire the shared env login

Once every active admin has a working `os-admin-` user (the reconciler reports zero pending):

1. Set `disable_env_credential_login: true` in `general_settings` (`values.yaml:922` block).
2. Remove `litellmUI.username/password` from values and the `litellm-credentials` Secret, and
   remove `config.litellmUiUsername/Password` from os-ui.
3. Break glass: an operator still has the master key and port-forward
   (`docs/components/litellm.md` "Direct access"). Document this in the runbook. There is no
   standing password login.

Rollback: unset the flag and restore the Secret value (kept in the operator vault for one release).

### 2.7 Audit (the OS is the system of record)

Append an `os_governance.audit_events` row (`actorKind: 'user'`) for:

| Action | When |
|---|---|
| `litellm.console.session` | a new LiteLLM session is minted for an admin (not per request) |
| `litellm.admin.provisioned` / `deprovisioned` / `blocked` / `password_rotated` | the reconciler's actions |
| `litellm.env_login.disabled` | step 2.6 |

Each row carries the uid, `litellm_user_id`, the dashboard key's token id (hash, not value) and
the outcome. What the admin then does inside LiteLLM is attributed to `os-admin-<uid>` in
LiteLLM's own tables (keys `created_by`, spend logs). The OS mirror (`tabs/admin/lib/gateway-mirror`)
can read those back, but LiteLLM has no audit API without Enterprise, so this is best effort.

### 2.8 Dashboard keys

Each UI login creates a 24-hour, $1 key in team `litellm-dashboard`. With 2.5, that is at most
about 3 per admin per day. The reconciler also deletes expired `litellm-dashboard` keys owned by
`os-admin-*` users once a day, so the key list stays readable. The shared agent key and per-system
keys are untouched (different team and alias).

## 3. Migration

1. Ship the reconciler with `OS_LITELLM_PER_ADMIN=0`: the plan is computed and shown in Platform
   health, nothing is applied.
2. Dev: set `=1`. Admins are provisioned. Open the console as two different admins and check in
   LiteLLM that actions show the right user. Demote one and check that access is gone within one
   debounce.
3. Fix or confirm the possible injection bug in section 1 first, because it decides whether SSO
   works at all today.
4. Prod after the owner tests dev and says go.
5. After a week, retire the env login (2.6) in a separate release.

## 4. Tests

| Level | Test |
|---|---|
| Unit | reconciler plan (create, delete, block, no-op, foreign users untouched); per-uid cache (TTL, single flight, eviction on demotion); cookie stripping for LiteLLM (2.5 a); no password in any log or trace |
| Contract (LiteLLM 1.109.1 container) | `/user/new` as `proxy_admin`; forced change then login works; login creates a `litellm-dashboard` key; `disable_env_credential_login` refuses the env login; deleting a user invalidates their session |
| Integration | role change admin → builder removes access (OS 403 and LiteLLM session dead); deactivation; two admins on one browser get their own identities |
| Independent verifier | checks LiteLLM attribution and the demotion path on dev |

## 5. Risks

| Risk | Mitigation |
|---|---|
| LiteLLM changes the login or password-change flow | contract test on every bump (`docs/ops/litellm-upgrade.md`) |
| All admins locked out (reconciler bug, env login already off) | the env login is retired only after a week of clean runs; break glass via master key and port-forward |
| Stale session after demotion | eviction first, then key block; strip browser cookies (2.5 a) |
| Dashboard key sprawl | session cache plus daily clean-up |
| Password store key lost | re-provision: set new random passwords through the admin API (master key). No user impact |

## 7. Open questions for the owner

1. **Admins only, or domain_admins too?** This design gives LiteLLM access to `admin` only, as
   today. Domain admins could get LiteLLM `internal_user` (their team's keys and spend), but that
   needs teams per domain to be modelled first.
2. **Break glass.** Is master key plus port-forward enough, or do you want one sealed emergency
   `proxy_admin` held offline?
3. **Session length.** 8 hours is proposed. Shorter means more dashboard keys. Longer needs the JWT
   lifetime raised.
4. **Cookie binding:** strip and inject server-side (recommended) or a signed uid cookie?
